How verl drives a GPU cluster with one Python process

RL post-training (PPO, GRPO) is really two programs tangled together: a small, ever-changing control flow — generate → score → advantage → update — and a giant, multi-GPU computation flow. verl keeps the control flow in one ordinary process (the single controller) and pushes the heavy work onto a fleet of Ray actors, one per GPU. This page is the mental model.

The one idea — Ray lets you call a Python class method as a remote procedure. verl wraps a group of those actors behind a proxy so that wg.generate_sequences(batch) — a plain method call on the driver — secretly splits the batch across every GPU, runs it in parallel, and merges the results back. The distributed code reads exactly like the single-process code.

The trick: one call, fanned out and gathered

Move the sliders and press Run a stage. A batch of DataProto rows enters the driver, gets chunked across the workers (auto-padded to a multiple of the world size), each GPU computes on its shard, and the outputs are collected back into one batch.

Faded cells are padding rows verl adds so the batch divides evenly across GPUs — they're sliced off again during collect. The driver itself holds the whole batch between stages; that's what makes the loop debuggable.

Why split control from computation?

Most distributed training is SPMD: launch N identical processes, every rank runs the same script. That's great for one model, but PPO juggles several models (actor, critic, reference, reward) with different parallelism — and you can't easily set a breakpoint to inspect a reward tensor when every rank is racing. verl decouples the two flows instead.

What "effective" means here

The driver doesn't just farm out work — verl uses Ray's primitives to pack the cluster tightly:

  • Placement groups with STRICT_PACK reserve a whole node's GPUs together, so the colocated hybrid engine can ship fresh policy weights to the rollout engine over intra-node NCCL — no checkpoint round-trip per step.
  • One Ray actor multiplexes many roles. create_colocated_worker_cls fuses actor + rollout + reference onto the same GPU set, so reserved hardware is never idle.
  • Async by default. Worker calls return Ray ObjectRef futures; independent stages overlap and only synchronize when a blocking collect needs the data.
  • Sleep / wake. During the training phase the vLLM rollout engine sleeps to free KV-cache memory, then wakes and receives updated weights before the next generation.
★
The whole PPO step is one readable loop in RayPPOTrainer.fit(). Each wg.method(batch) fans out to every GPU; compute_advantage(...) is plain Python on the driver. That separation is the entire HybridFlow design.

The loop, in eight lines

# verl/trainer/ppo/ray_trainer.py — RayPPOTrainer.fit()  (paraphrased)
for prompt in dataloader:
    output       = actor_rollout_ref_wg.generate_sequences(prompt)   # fan-out → vLLM on N GPUs
    old_log_prob = actor_rollout_ref_wg.compute_log_prob(output)
    ref_log_prob = ref_policy_wg.compute_ref_log_prob(output)
    values       = critic_wg.compute_values(output)
    rewards      = reward_wg.compute_rm_score(output)
    advantages   = compute_advantages(values, rewards)              # runs on the driver
    actor_rollout_ref_wg.update_actor(output.union(advantages))
    critic_wg.update_critic(output)

Glossary
Single controller
The one driver process running the RL algorithm. Holds the batch, holds no model weights.
Worker / Ray actor
A @ray.remote object pinned to one GPU that holds model shards and does the math.
Control flow
The algorithm's high-level steps. Small, sequential, changes per algorithm.
Computation flow
The neural-net work: rollout, forward, backward, optimizer. Multi-GPU, rarely changes.
Dispatch
Splitting a batch across workers — e.g. DataProto.chunk(world_size) with auto-padding.
Collect
Merging each worker's output back into one DataProto via concat.
DataProto
The batch container that travels driver↔worker and knows how to chunk/concat itself.
Hybrid engine
Training and inference colocated on the same GPUs, taking turns via sleep/wake.
SPMD
Single-Program-Multiple-Data — the lockstep model verl deliberately avoids for control flow.
