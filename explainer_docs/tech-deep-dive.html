How verl's single controller turns one method call into a cluster-wide job

verl runs the PPO/GRPO control loop in one driver process and the model math across Ray actors, one per GPU. The bridge is verl.single_controller: a @register decorator tags each worker method with a dispatch policy, and a RayWorkerGroup proxy uses that policy to split a DataProto across workers, fire N async Ray RPCs, and concatenate the results. Below is the exact call chain for one stage — generate_sequences — and how the GPUs get reserved and colocated underneath it.

verl/trainer/main_ppo.py · run_ppo() / TaskRunner

The entrypoint calls ray.init(), then wraps the controller as a Ray actor — ray.remote(num_cpus=1)(TaskRunner) — and runs it with ray.get(runner.run.remote(config)). TaskRunner.run() builds a RayPPOTrainer and calls fit(). The driver is a single process and is deliberately kept off the resource-poor Ray head node.

verl/single_controller/base/decorator.py · @register

This is the heart of the design. @register doesn't change what the method does — it attaches a dispatch policy under a magic attribute so the WorkerGroup can later discover it. DP_COMPUTE_PROTO means "split the input DataProto across data-parallel ranks, concat the outputs."

show source 
# the decorator (decorator.py)
MAGIC_ATTR = "attrs_3141562937"

def register(dispatch_mode=Dispatch.ALL_TO_ALL, execute_mode=Execute.ALL, blocking=True, ...):
    def decorator(func):
        @wraps(func)
        def inner(*args, **kwargs):
            if materialize_futures:
                args, kwargs = _materialize_futures(*args, **kwargs)
            return func(*args, **kwargs)
        attrs = {"dispatch_mode": dispatch_mode, "execute_mode": execute_mode, "blocking": blocking}
        setattr(inner, MAGIC_ATTR, attrs)
        return inner
    return decorator

# the worker method (verl/workers/engine_workers.py)
class ActorRolloutRefWorker(Worker):
    @register(dispatch_mode=Dispatch.DP_COMPUTE_PROTO)
    def generate_sequences(self, prompts: DataProto): ...

verl/single_controller/base/worker_group.py :185 _bind_worker_method

When the RayWorkerGroup is built, it walks every method of the worker class. For each one carrying MAGIC_ATTR, it looks up the dispatch_fn / collect_fn pair in DISPATCH_MODE_FN_REGISTRY and the execute_fn by execute-mode, then synthesizes a brand-new method on the group via func_generator. After this, wg.generate_sequences exists and is callable like a local method.

show source 
# worker_group.py — binding (condensed)
for method_name in dir(user_defined_cls):
    method = getattr(user_defined_cls, method_name)
    if hasattr(method, MAGIC_ATTR):
        attrs = getattr(method, MAGIC_ATTR)
        dispatch_fn = DISPATCH_MODE_FN_REGISTRY[attrs["dispatch_mode"]]["dispatch_fn"]
        collect_fn  = DISPATCH_MODE_FN_REGISTRY[attrs["dispatch_mode"]]["collect_fn"]
        execute_fn  = getattr(self, get_predefined_execute_fn(attrs["execute_mode"])["execute_fn_name"])
        func = func_generator(self, method_name, dispatch_fn, collect_fn, execute_fn, attrs["blocking"])
        setattr(self, method_name, func)   # wg.generate_sequences now exists

verl/single_controller/base/decorator.py · dispatch / collect

On the driver, calling wg.generate_sequences(batch) runs the generated wrapper: dispatch_dp_compute_data_proto chunks the batch into world_size shards (auto-padded so it divides evenly); execute_all fires one async Ray RPC per worker and returns ObjectRef futures; collect_dp_compute_data_proto concatenates the gathered results back into a single DataProto and strips the padding.

show source 
# dispatch: split a DataProto across DP ranks (decorator.py)
def dispatch_dp_compute_data_proto(worker_group, *args, **kwargs):
    splitted_args, splitted_kwargs = _split_args_kwargs_data_proto_with_auto_padding(
        worker_group.world_size, *args, **kwargs)
    return splitted_args, splitted_kwargs

# what the generated wrapper does
args, kwargs = dispatch_fn(self, *args, **kwargs)   # N shards
refs = execute_fn(method_name, *args, **kwargs)      # N async Ray RPCs → ObjectRefs
return collect_fn(self, ray.get(refs)) if blocking else refs   # concat back

verl/single_controller/ray/base.py :131 get_placement_groups

Where do the GPUs come from? A RayResourcePool turns "nodes × GPUs-per-node" into Ray placement groups with the STRICT_PACK strategy — every bundle is one GPU, and all bundles of a group are forced onto the same node. That node-locality is what lets colocated training and inference move weights over fast intra-node NCCL.

show source 
# ray/base.py — one bundle == one worker == one GPU
bundle = {"CPU": self.max_colocate_count}
if self.use_gpu:
    bundle[device_name] = 1
pg_scheme = [[bundle.copy() for _ in range(n)] for n in self._store]
pgs = [placement_group(bundles=b, strategy="STRICT_PACK", ...) for b in pg_scheme]
ray.get([pg.ready() for pg in pgs])     # block until the cluster reserves them

verl/single_controller/ray/base.py :988 create_colocated_worker_cls

To avoid giving each role its own idle GPUs, verl fuses roles onto one actor. create_colocated_worker_cls dynamically builds a WorkerDict that instantiates each sub-worker and re-exports their registered methods under role prefixes — so a single Ray actor per GPU serves actor + rollout + reference. spawn() then hands back one WorkerGroup view per role.

show source 
# ray_trainer.py — init_workers(): one colocated actor per GPU
for resource_pool, class_dict in self.resource_pool_to_cls.items():
    worker_dict_cls = create_colocated_worker_cls(class_dict=class_dict)
    wg_dict  = self.ray_worker_group_cls(resource_pool=resource_pool, ray_cls_with_init=worker_dict_cls)
    spawn_wg = wg_dict.spawn(prefix_set=class_dict.keys())   # one WG per role
    all_wg.update(spawn_wg)

verl/trainer/ppo/ray_trainer.py :1362 fit()

Now the loop reads like single-process code. Each wg.method(batch) is one driver call that fans out to all GPUs; compute_advantage(...) is plain Python on the driver, operating on already-gathered data; and after update_actor the new weights are synced to the sleeping rollout engine before the next generation. Swapping FSDP for Megatron, or changing placement, never touches this loop.

show source 
# ray_trainer.py — fit() (paraphrased order)
gen_out  = self.async_rollout_manager.generate_sequences(gen_batch)   # gen; then sleep replicas
reward   = self._compute_reward_colocate(batch)                       # rm_score / verifiers
old_lp   = self.actor_rollout_wg.compute_log_prob(batch)               # proximal anchor π_old
ref_lp   = self.ref_policy_wg.compute_ref_log_prob(batch)            # for KL (optional)
values   = self.critic_wg.compute_values(batch)                       # if use_critic
batch    = compute_advantage(batch, adv_estimator=...)              # ON THE DRIVER
self._update_critic(batch)
self._update_actor(batch)
self.checkpoint_manager.update_weights(self.global_steps)          # sync → rollout

Gotchas

  • Every driver↔worker hop serializes a DataProto. Keep outputs as DataProtoFutures and use blocking=False to overlap stages and cut round-trips.
  • create_colocated_worker_cls requires roles to share one placement group. For different parallel sizes per role, give each role its own ResourcePool instead.
  • Don't schedule the driver (main_task) on the Ray head node — it holds the whole batch and is memory-hungry; the head usually has little spare RAM.
